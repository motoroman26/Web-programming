# ADR 0005: Автентифікація через JWT і рольовий доступ (RBAC)

**Статус:** Прийнято
**Дата:** 2026-11-15

## Контекст

DocuFlow зберігає внутрішні документи компаній: статут, накази, посадові інструкції. Потрібно, щоб:
- кожна компанія бачила лише власні дані;
- працівники мали різні права (хтось лише читає, хтось редагує, хтось керує людьми);
- фронтенд на чистому HTML/JS міг працювати з API без складних бібліотек.

## Рішення

1. **Реєстрація компанії.** `POST /api/auth/register` в одній транзакції створює робочий простір (`workspaces`), користувача і запис у `workspace_members` з роллю `owner`.
2. **Паролі** зберігаються лише як bcrypt-хеш (10 раундів, сіль усередині хешу).
3. **JWT.** Після входу клієнт отримує токен на 12 годин `{ sub: userId, ws: workspaceId }`, підписаний HS256 ключем `JWT_SECRET`. Клієнт передає його в заголовку `Authorization: Bearer <token>`.
4. **Роль читається з БД на кожному запиті** (middleware `api/middleware/auth.js`). Якщо адміністратор змінив роль чи видалив працівника, це діє одразу, а не через 12 годин.
5. **Ролі (RBAC)**, кожна наступна має всі права попередньої:

   | Роль | Права |
   |---|---|
   | `viewer` (Глядач) | читати сторінки, файли, оргструктуру; шукати |
   | `editor` (Редактор) | + створювати/редагувати сторінки, блоки, файли; кошик |
   | `admin` (Адміністратор) | + працівники, оргструктура, остаточне видалення з кошика |
   | `owner` (Власник) | + призначати інших власників |

   Правило записане в одному місці: `backend/domain/Member.js` (`can(role, permission)`), а перевіряється в шарі `service/`.
6. **Ізоляція компаній.** Кожен SQL-запит у репозиторіях містить `workspace_id = $1` з токена. Чужа сторінка повертає 404, а не 403, щоб не підтверджувати, що вона існує.
7. **Захист від підбору пароля.** Не більше 10 спроб входу за хвилину з однієї IP (429 + `Retry-After`). На неправильний пароль і неіснуючий email — однакова відповідь `INVALID_CREDENTIALS`.

## Альтернативи

- **Сесії в cookies.** Потребують CSRF-захисту і сховища сесій. JWT простіше для API та для кількох реплік у Kubernetes.
- **Роль усередині JWT без перевірки в БД.** Менше запитів до бази, але зміна ролі не діяла б до закінчення токена. Обрали коректність.
- **OAuth / зовнішній провайдер.** Зайве для навчального проєкту, але архітектура дозволяє додати його пізніше.

## Наслідки

- Кожен захищений запит робить один додатковий простий запит до БД (за первинним ключем).
- `JWT_SECRET` обов'язковий у production (сервіс не стартує без нього) і зберігається в Secret Kubernetes.
- Токен лежить у `localStorage`, тому весь фронтенд вставляє дані лише через `textContent` (захист від XSS).
