# ADR 0006: Зберігання файлів-документів у PostgreSQL

**Статус:** Прийнято
**Дата:** 2026-11-15

## Контекст

Компанії прикріплюють до сторінок скани статуту, наказів, договорів (PDF, Word, Excel, зображення). Бізнес-документ обмежує систему: це **не** файлове сховище, файли — лише додатки до регламентів. Типовий розмір — від кількох КБ до кількох МБ.

## Рішення

- Файли зберігаються в таблиці `attachments` у колонці `BYTEA` разом із метаданими: назва, MIME-тип, розмір, хто й коли завантажив.
- Максимальний розмір — **10 МБ**. Його перевіряють три рівні: multer (обрізає потік), сервіс (`FILE_TOO_LARGE`) і обмеження `CHECK` у БД.
- Дозволені лише документи й зображення (білий список MIME-типів у `domain/Attachment.js`). Виконувані файли відхиляються.
- Кириличні назви файлів декодуються з latin1 в UTF-8 і очищаються від небезпечних символів (`/ \ : * ? " < > |`).
- Скачування: `GET /api/attachments/:id/download` з `Content-Disposition: attachment; filename*=UTF-8''...` (RFC 5987).
- Список файлів сторінки повертає лише метадані, без вмісту, щоб не вантажити мережу.

## Альтернативи

- **Файлова система або volume.** Потребує окремого бекапу і спільного диска для кількох реплік API у Kubernetes.
- **S3 / MinIO.** Правильно для великих обсягів, але додає ще один сервіс в інфраструктуру навчального проєкту.

## Наслідки

- Один бекап (`pg_dump`) зберігає і текст бази знань, і документи. Видалення сторінки каскадно видаляє її файли.
- Репліки API залишаються stateless, тож їх можна вільно масштабувати.
- Перегляд: якщо обсяг файлів компанії перевищить ~10 ГБ або знадобляться файли понад 10 МБ, переносимо вміст у S3-сумісне сховище. У БД тоді лишаються метадані й ключ об'єкта.
